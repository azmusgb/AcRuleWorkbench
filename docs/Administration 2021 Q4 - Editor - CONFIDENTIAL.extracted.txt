Getting Started 
The FormWorks Editor is a GUI (Graphical User Interface) tool that is used to define objects (pages, documents, 
and batches) in conjunction with the processing steps and resources associated with those objects in a 
FormWorks 5.0 system.  The Editor provides a framework for maintaining common configuration information for 
each object; and the information is stored in the FormWorks database (.FWD).  Process-specific and resource-
specific configurations are maintained by multiple Plugin Configuration Modules (PCMs) which are automatically 
loaded by the Editor when it is opened. 
Note: The encryption protocols, keys and strategies have been upgraded for the 
FormWorks system in this release for increased data security. Refer to System 
Administration user guide for more information 
 
Note:  Key Terms, Definitions, Configurations, Process and Functions described within this 
document are in reference to the base FWEdit functionality.   
 
PCM Modules may alternately be referenced by their individual process name within this 
document 
 Key Terms 
Term Definition 
AC 
Auto Capture, is a specialized version of the current Data Validation (DV) 
worker.  It consists of a rule processing engine; plug in rules, tables, and a 
worker shell.  The same engine plugs into KE and should be able to be 
plugged into virtually any worker.  The AC Worker may be used for both 
validation and for auto capture processing.  The difference between auto 
capture and data validation are the types of rules implemented and the 
position in the system route.  Generally, FormWorks 5 systems are structured 
so that references to ACI are to Auto Capture before OCRepCrit and ACII refer 
to Auto Capture after OCRepCrit. 
AEG (OpenText) Software character recognition engine (company originally Advanced 
Engineering from Germany, now AEG is a product of OpenText). 
Agent 
The System Administration service that is part of FormWorks 5.  Agent 
provides functionality not provided in prior FormWorks versions but also 
replaces several contrasting utilities (JumpStart, FMD, Table Updater, and 
Config Server) with a single application.   
Functionally, Agent is a central management point of a FormWorks 5 system.  
Agent controls file and configuration updates to the individual machines and 
also runs as a service allowing Navigator to control remote workers and 
provide access to remote log files.   
Note: On an individual’s machine where a non-web 
process may run, LaunchPad will connect to the Agent 
to request for processes to start and stop (SQA Viewer, 
Inventory Client, and Scan).

Term Definition 
Batch 
A FormWorks Batch is a group of documents that can have one or more types 
of documents.  An operator enters a batch into the system using an Inventory 
client to specify various options, and to enter values for batch attributes.  
These options and attributes are configured through the Inventory Resource 
PCM.  Typically, a batch is also the grouping of paper placed into a scanner as 
a single unit of work. 
BWS 
Background Worker Shell is an executable capable of loading and running a 
custom worker DLL.  The DLL contains all of the information necessary to 
process its work; the BWS only oversees the management of resources.  The 
BWS is by design to be utilized only by approved FormWorks support 
personnel. 
CFD 
Compressed FormWorks Database; distributed to each worker in a Formworks 
system.  The CFD is the file loaded and run by those workers with a PCM in a 
FormWorks system.  The CFD contains the business rules and other worker 
settings specific to a particular system.   
Collator 
This worker assembles the batch into document(s) by grouping pages scanned 
with the same DCN together.  The information is written to the work record of 
the batch.   
Component A unit of software that is produced by the FormWorks Development Team for 
the FormWorks application. 
Data Validation The role of Data Validation (DV) is to evaluate field contents in context and 
determine whether or not the data is logical. 
DCN 
Document Control Number - A unique number assigned to each document in a 
system, usually imprinted on the form as its scanned.  The DCN is reserved by 
Inventory and assigned by Scan (for scanned documents). 
Deskew 
When scanning in documents one thing that could happen is the possibility of 
pages not feeding properly, so some of the images will be appear slanted.  
Deskew is a feature that resolves this problem.  After scanning in a document, 
if the document’s text or images are at a slight angle, the FormWorks software 
will auto-rotate the document so that the alignment is corrected. 
Document Fields 
Document level fields are fields that are attached to the document as a whole, 
rather than to a specific page of a document.  Document level fields are all 
non-imaged, since they could occur anywhere within the document. 
FIP 
FIP (Forms Image Processing) is the FormWorks component that identifies 
forms and assigns PageIDs.  FIP also reads any checkboxes (also known as 
OMR or Optical Mark Recognition), removal (form instructions, lines), and 
deskews scanned images.  FIP manipulates images to have the best quality 
for OCR (reads text on the page) and performs the mark recognition.  It is the 
responsibility of the FIP worker to register and clean-up images.  The FIP 
worker generates the Removed Image, OCR, and History file for each 
document.

Term Definition 
FWD 
FormWorks Database; contains configuration information for a FormWorks 
system.  The FWD is the uncompressed FormWorks database used by 
FWEdit.  FWEdit is responsible for creating the .CFD database format. 
FMD 
The File Migration Daemon is a service imbedded in the Agent.  When the 
LWM receives work records, the FMD is responsible for moving all required 
batch files (images, OCR, and history) to the local host.   
Note: The FMD was a standalone process in FormWorks 4 and prior versions. 
FWEdit, FWE; 
Editor 
FormWorks Editor drives much of the system and uses many flexible functions 
to assist in creating rules.  It is through FWEdit that users may configure the 
system. 
FW5 FormWorks 5 
JDAY 
Julian Date, consisting of a year and a day number starting at 1 for each new 
year and incrementing for each subsequent day throughout the year.  For 
example, February 1, 2012 is the 32nd day of the year, so the JDay would be 
12032. 
KE 
This worker presents any fields that were rejected by a business rule to an 
operator for correction via a graphical user interface.  An operator may then 
correct the data, override the reject, or reject the document.  Any table lookup 
that could not auto plug is to be completed by the operator choosing an entry 
from a selection list.  Most often, KE is the second keying step (after KFI) 
within a typical system configuration. 
KFI 
Key From Image, a type of KE.  The interface is identical to KE except there is 
no information in the data window from OCR.  KFI is used to key images that 
failed to register properly at FIP.  At KFI, the entire form is keyed.   
Note:  While not common, in some systems there is not an actual KFI step, 
instead, formats that fail FIP will be Keyed From Image in a normal KE step. 
LWM 
The Local Work Manager component runs as a service on all FormWorks 
hosts (each host will have its own LWM).  The LWM receives work records 
from the MWM and distributes the records to the appropriate worker on the 
host on which the LWM runs.  The LWM service must be running for any 
worker to run. 
MWM 
Master Work Manager is a component run on the QManager machine.  It is 
responsible for assigning batches to workers, tracking the status, location of all 
batches, and monitoring the status of all hosts and workers.  The MWM must 
be running for work to move through the system.  For a given system, there 
may be only one MWM. 
OCR 
Optical Character Recognition, this worker attempts to read the data in a 
monochrome TIFF image.  The system stores read data and confidences of 
the data to the OCR file.  OCR occurs after FIP. 
OCRepair An interactive worker to supplement the OCR engine in the Data Capture 
process.  Any character "guess" from OCR that does not meet the Confidence

OCRepCrit 
OCRepair Critical, an optional stage (located between ACI and ACII) where an 
implementation of OCRepair is used to repair the "critical" fields, (a "critical" 
field usually means that the field is an essential part of a larger lookup).  For 
example, the Member ID, DOB and Last Name are repaired.  The system 
matches this information within the database negating the need to repair the 
address, first name, etc. 
OCRepSig 
OCRepair Signature is for entering signatures only.  It is most often used to 
capture Box 31 on a HCFA for database matching purpose.  OCRepSig is not 
part of a standard FW5 configuration. 
OMR 
Optical Mark Recognition; OMR fields are fields that consist of checkboxes 
instead of text.  OMR analyzes the image of a form and determines if a 
checkbox has been filled in.  OMR is performed by FIP. 
PCM 
Plugin Configuration Module or sometimes called the Process Configuration 
Module; a PCM module is loaded by the Editor to manage the configuration of 
a process or a resource in a FormWorks system.  Essentially, a PCM is a DLL 
with specific entry points the Editor uses to load and invoke the module.  A 
single PCM may only support one Processing type, but it may support any 
number of processes or resources of that type. 
Processing Step Each processing step is a distinct stage, in which some operation is performed 
on the data. 
Processing Type 
The Processing Type describes the nature of the work being performed at a 
given step.  The Processing Type determines which FormWorks worker is 
used at a particular step, and which PCM is used to maintain the configuration 
for that step. 
RCM Resource Configuration Module; a PCM for a Resource (see PCM). 
Resource A configuration object that is shared by one or more processes.  Each 
resource has a basic type that defines and describes what the resource is 
(Fileref, Function, Table, etc.).   
Resource Type 
Every resource in a FWD has a resource type that describes what it is (Fileref, 
Table, etc.).  The resource type determines which RCM is responsible for 
maintaining its configuration. 
SFD/STC Plus 
The SFD is the compressed version of the FWD (also referred to as STC Plus) 
intended to increase the speed of loading, saving, exiting the FormWorks 
Editor) and when called is used to build or fulfill specific functions.  The 
FWEditor may always access the SFD.  The STC library is responsible for 
reading and writing all three forms of the FW database (SFD/CFD/FWD) and 
also for providing a generic interface to each. 
Slot A slot is a location for a piece of data to output.  Slots are defined/named in a 
template set resource.

Term Definition 
Store 
A background worker responsible for the output of a system.  Store may be 
configured to output flat files, 837 files, database output, XML, .TIFF (and other 
formats).  A batch's state is typically changed to "Retired" after a batch has 
moved through the Store worker. 
Variant A graphically different version of a page.  Each page object in the FWD may 
have a single variant or multiple variants. 
Worker 
(Background 
Worker) 
Worker/Background Worker 
Workers refer to interactive workers involving some degree of human 
interaction.  Examples of Workers are KE, KFI (and others). 
Background Worker (modules) are unattended workers (no human interaction), 
typically running at all times (may have user configured sleep times).  
Background workers include FIP, OCR, Collator, AC-I, AC-II, DV, Store, 
Historian, SQAC, StatStore, Inventory Server (among others).   
Word Record 
A unit of work that passes through the FormWorks system.  A Batch can be 
composed of one or more Work Records and may be split by client needs 
based upon: 
Number of Documents. 
Particular routing needs or requirements. 
Exception processes.

Term Definition 
Work Record File Serves as a "Master File" for each Work Record; every Work Record has 
one Work Record File(WRF).  The Work Record Files contain information at 
the record level followed by a series of Items and information about those 
items. 
Record – General batch information such as the Batch Type, Inventory 
information, and Routing information. 
Item – Typically each page of the work record DCN (Document Control 
Number) and PageID, Deskew information and other page or document 
attributes. 
Item 0 represents the Work Record itself. 
Subsequent Items contain information about the contents of the Work 
Record (documents, pages, etc.),

OCR File Created at FIP.  The OCR file contains the claim data and is modified by

FWD Tree Component Terms 
Term Definition 
Variant A graphically different version of a page.  Each page object in the FWD may 
have a single variant or multiple variants. 
Resource(s) A resource is a configuration that may be shared by one or more processes.  
Each resource has a basic type that defines and describes what the resource 
is (Fileref, Function, Table, etc.).   
Processes Each processing step is a distinct stage, in which some operation is 
performed on the document.  The FWD may contain Inventory, Scan, FIP,

Plugin Configuration Module(s) 
Important:  The processing steps and workflow models presented in this document are 
representative of a typical FWEditor Express environment.  Users of this document are 
to note that it is anticipated that FormWorks production processing environments will 
differ from the representative FWEditor Express environment illustrated in this 
document. 
While FormWorks Editor allows the user to directly manipulate process-independent information in the FWD, 
Plugin Configuration Modules (PCMs) that are dynamically loaded into FormWorks Editor are used to edit all 
process-specific and resource-specific information.  This design enables new versions of workers and their 
configuration objects to be introduced without having to update the Editor. 
When the FormWorks Editor is started, all of the available PCMs are loaded.  Each of the PCM objects are 
queried to determine the processing type supported, as well as what type of FWD information the PCM operates 
on.  For example, the FIP PCM may indicate that it operates on batch, page, and page variant data, while the 
Store PCM registers as operating on page and document data.

When setting up an FWD using the Editor, users designate the processing steps the data will go through.  Each of 
these steps has a base processing type that is specified by a loaded object.  If the database contains a 
processing step that uses a base type not defined by a PCM, the Editor will not allow users to edit the 
configuration of that particular processing step. 
By using a two-tier approach of processing steps and base processing type, users may have multiple workers of 
one type.  For example, many systems have OCRepNum (to repair numeric fields) and OCRepair (to repair 
alphanumeric fields).  Both of these steps have the base process type of OCRepair and their configurations are 
maintained by the same PCM.

Events 
For each type of processing (Batch, Document, Page, and Page Variant, etc.) the PCM that supports the 
processing type receives edit events which are generated when editing the process configuration for any FWD 
object. 
Events are also generated when the information in the public section (Pages/Batches) of the FWD is changed 
(such as deleting an object, or changing a field’s base type).  Each PCM for all of the processing steps is notified 
of the change, giving each configured process an opportunity to update its configuration accordingly. 
Finally, before the deletion of any public data (Pages/Batches), each PCM is given a chance to indicate the 
consequences of the deletion.  If a PCM indicates that there may be a problem, users have a chance to cancel 
the deletion.  If the user elects to continue, the PCM receives a deletion event.   
For example, if a field is deleted from a page, the AC object may display a warning that the field is used in two 
rules.

Register the License Key in FWEditor 
The FWD license is a separate key generated by FWEdit and stored in the .CFD file.  This key is used by 
Background Worker Shell (BWS) to verify that the .CFD file was produced from a licensed FWEdit.  
To verify that FWEdit is properly licensed and secure, verify that the license.cfg file is present in a known location 
for the system.  On load of the FWEditor, an open dialog box is displayed, this screen prompts for the license file 
with the default extension of ".cfg" selected.   
Note: It is not necessary that the extension of the license file be "cfg" and there is an option 
to select a file with any extension.  
Once the license key has been validated and the FWEditor loads, the user may proceed with working with the 
FWEditor application.  When all the changes are done and the user chooses to build the CFD file, the editor then 
takes the CustomerID, .FWD build version and generates a unique code to build a separate license key that is 
stored in the .CFD file.  When the BWS executable loads the .FWD for several of the workers, the license key is 
validated against the information in the .CFD file.  If the license key is found to be valid, then the RRIBWS 
executable continues to load the worker.  If the license key is found to be invalid, then an error message stating 
that the FWEdit license was invalid is logged into the log file for that worker and an error alert is also issued.

Output Driver Resource  
An Output Driver is used to send formatted data that has made its way through the FormWorks pipeline to its final 
destination.  This destination may be a file, fileref, or database, etc.  Each destination requires a unique driver for 
one type of output (ODBC, fixed-length records, XML, etc.). 
Note:  The Output Driver and Destination are a unique one to one relationship.  


===== PAGE 95 =====

be utilized at the same time by the Store Worker. 
Note:  The order in which the output drivers are listed in the Store Process (Store 
Configuration tab) is the order in which output is executed.   
Configuration information is passed to the Output driver where the validity of the information received is confirmed 
against the information contained in the configuration.  After the information has been processed, the driver 
cleans up after itself via the dispose function (within the driver).   
Note: The driver is notified automatically whenever the Worker begins or ends the 
processing of a batch or document.

Optical Mark Recognition Fields (OMR) 
OMR, or Optical Mark Recognition fields are checkboxes, signatures, or other fields that simply need to be 
checked for a ‘mark’ inside the field.  The data is not interpreted and the system merely judges if there is a mark 
or not inside the field.  Every OMR field has two levels:  
• The OMR field itself, which contains all the possible choices. 
• The OMR subfields, which represent the individual checkboxes or options.   
As an example, the OMR field Relationship to employee may contain (within) the subfields self, spouse, child and 
other. 
 
Unlike text fields, OMR fields are read by FIP Worker, which analyzes only for the presence or absence of a mark 
in the box.  This "mark" may take the form of a check, X or a line (either vertical, horizontal or diagonally) within 
the box.

Collator Process 
The Collator (Collator System) assembles pages into documents and assigns a document ID.   
Typically, the Collator determines which pages belong together through one of several collation techniques 
(described below).  When a collation technique is selected for the Collator process, it is a system-level setting 
used as a default.  At the batch level, users may specify a different technique if necessary.  See Collator: Batch 
Processing for more information. 
As a best practice, select a collation technique that is reliable (identifies all pages as part of a document). 
Collation Techniques 
• Fixed Number Of Pages Per Document – Uncollated pages are moved into documents consisting of a 
fixed number of pages.  If there are not enough pages to make an entire document, the pages available 
are placed into a document, but no error is set.  This technique should only be used when all documents 
in the batch contain "n" pages, and are sorted correctly.  
• Attributes Change Values – Collator compares the values of an attribute or set of attributes, usually DCN.  
The first uncollated page is assumed to be the first page of a document; a new document is created when 
the value of the specified attribute(s) changes.  All pages with the same value for all specified attributes 
are moved into a document.  The separator page (if there is one) can be deleted based on the attribute 
that changed.  
Note: The Fixed Number of Pages Per Document or Attributes Change Values technique 
never results in uncollated pages. 
• Attributes Present – Collator looks for the presence of one or more specified attributes to determine if a 
page is a separator page, and creates a new document each time a separator is found.  Each successive 
page not having the specified attribute(s) is moved into the new document.  The separator page can be 
moved into the new document or deleted based on the attribute found.  
• PageIDs Used As Separators – Collator is configured with a set of PageIDs that are separator sheets.  
When Collator finds a page with a separator PageID, a new document is started.  All successive pages 
that are not separators are moved into the document.   
Note:  PageIDs used as Separators are configurable as a Batch-Level option only.

TwainScan Process 
The FormWorks TWAINScan application allows the operator to scan batches into the system using the 
specifications set in Inventory Client.  The TWAINScan application traditionally picks up the barcode from the 


===== PAGE 192 =====
 
  
www.fisglobal.com           192 
 
FormWorks 2021 Q4 Editor Administrator Guide 
batch cover sheet, the retrieves the batch information from the inventory server.  Based upon the batch type, the 
TWAINScan application will initialize the scanner with the appropriate settings for the batch. 
TWAINScan provides both a system level configuration and an individual batch level configuration.  
At the system and process level, TWAINScan communicates to the scanning application where to locate the 
Inventory Server used to retrieve batch information, enter batches, and the fileref for scanned images.  All other 
configuration for TWAINScan can be done either at the process- or batch-level.  Any setting at the process level 
will be used for all batches unless individual settings are modified for a batch.   
Note: The batch-level settings do not show modifications made at the process level, though 
they are indeed inherited when they are set to use process default (grayed out).  Also, 
Fileref is configured within the Resources tab. 
Custom batch level settings are configured through the TwainScan Batch Configuration window. 
• TWAINScan is configured at the system level within the TwainScan Process Configuration window. 
• TWAINScan is configured at the batch level within the TWAINScan Batch Configuration window. 
Important: Users must set up FileRef and Inventory resources before 
configuring TwainScan.  
• Fileref Name – Specify the fileref that scanned images will be saved to (usually OriginalImage) 
• Device Type or Device Alias – Select Device Type to specify the scanner by type (scanner or disk) in the 
drop down list.  Select Device Alias to specify the scanner by name.  Type in the source name in the box 
to the right. 
• Inventory Server – Select the name of the Inventory resource. 
• User Name and Password – The name and password Scan used to log into the Inventory server.  If the 
Inventory server uses an authentication database, such as auth.db, the password must be entered.

Before working with AC rules, become familiar with the following terms: 
• Function – An operation that is called from a rule list, and typically tests or modifies field contents.  All

possible status result of the function. 
• Parent Rule – A rule that contains one or more sub-lists of actions. 
• Action – A rule list that executes when the evaluation of a rule arrives at a particular status.

AC Function Types 
The list below contains general descriptions of the rule categories.  Additional information about specific functions 
may be found within the FormWorks AC Functions document. 
• Intrinsic – An intrinsic function is built into the AC engine (as opposed to being contained in a separate 
rule DLL).  Intrinsic functions perform specialized tasks, such as calling other functions or interacting with 
the work record.  
• Custom (Tcl Procedure) – Used to write new rules for specialized customer needs.  AC/Tcl functions 
incorporate Tcl scripts into them.  These functions are not implemented in the Standard AC Plugin DLL 
(acsrules.dll), but in their own custom DLL (actcl.dll).  Please refer to the internal website for additional 
information. 
• User-Defined – These are functions that call other functions, and are typically used for complex rules.  
The user creates the function implementation as a Function resource in the Editor, defining named field

www.fisglobal.com           214

list parameters and status results.  Generally, a user-defined function is a rule list, in which the rules refer 
to the named field list parameters rather than any specific fields.  These field lists are expanded against 
the list of fields passed to the user-defined function when it is called by an AC rule. 
• Testing – Checks the contents of a field, without changing it, and then returns a status.  Contained in 
acsrules.dll. 
• Formatting – Changes the representation of information in a field.  Formatting functions generally do not 
reject fields or return status.  Contained in acsrules.dll. 
• Rectifying – Functions that examine confidence levels to determine whether characters should be 
accepted or repaired.  Contained in acsrules.dll. 
• Table – Functions for checking selection lists and plugging values from tables.  Contained in acsrules.dll. 
• Store – Store-specific functions used to facilitate Store template population and formatting requirements.  
Contained in acstore.dll. 
• Deprecated – These functions are older versions of functions found in other categories.  As a best 
practice, they should generally not be used and are only present for backward compatibility with existing 
rules.  When the Editor finds a rule using a deprecated function, it issues a warning.  The user should 
replace any deprecated functions whenever practical.

and use the same procedures.  Functions are further documented with the AC Functions

The FormWorks system has been enhanced to include a new standard Barcode worker that is capable of reading 
both one-dimensional (1D) and two-dimensional (2D) barcodes. 
Barcodes provide an accurate, efficient way of labeling and organizing data, and allow for its easier 
retrieval.  The characteristics of both barcode types are as below: 
• 1D barcodes can store up to 30 alphanumeric characters, and are also known as linear barcodes. 
• 2D barcodes are generated in various geometric shapes and can store large amount of data in a very 
small area (up to 7089 characters).  It supports numbers, characters, pictures, voice and other binary 
information. 
The barcode worker supports DataMatrix, PDF417, and QR types of 2D barcodes, in addition to most 
linear barcode types. 
Users can define the maximum number of characters that can be read from the barcode using the 
'MaxBarcodeLength' attribute in the Barcode.cfg file.  Maximum barcode length that is allowed is 128.   
Value assigned to the MaxBarcodeLength attribute should always be greater than the MinBarcodeLength 
value. 
Note - If the Barcode worker is configured for OCR Field output, the barcode geometry will 
be saved to the OCR file.  Barcode geometry is saved in the OCR format: length, X, Y, W, 
and H where length = number of characters in the Barcode, and  X, Y, W, and H are 
location pixels. 
Licenses required 
The barcode worker uses the ClearImage Barcode Recognition Engine developed by Inlite Research Inc.  
Depending on the types of barcodes to be read, runtime licenses for one or more of the following products are 
required: 
• ClearImage Barcode 1D Basic or Pro 
• ClearImage DataMatrix 
• ClearImage PDF417 
• ClearImage QR 
Usage 
The FormWorks system will read the barcodes printed anywhere in a document, and return the encoded data as 
part of the document that can be used for further processing.  Typical uses of this worker are:

specified for the variant.

OCR 
• Lost Characters – If characters are consistently being lost from the right side of a field, the noise 
suppression may have inadvertently be set.  Right-click the page name (not the variant), Select 
Processing > OCR.  In the OCR dialog box, select the field name, and check the noise suppression 
settings. 
• Misread Characters – Select a character set that accurately reflects the expected contents of the field.  
For example, a field labeled Provider Number may actually (correctly) contain alphanumeric characters.  If 
a numeric only character set is selected, OCR will read B as 8, D as 0, and so on.  It is better to use an 
alphanumeric character set even if the character is read with a low confidence and must be keyed. 
 
Note: Verify that the page settings at the variant level have been overridden.  Right click 
the Variant Name, select Processing > OCR.  Remove any unnecessary overrides.  The 
page level and variant level windows are very easy to confuse. 
 
Troubleshooting 
Looping 
Looping, is in reference to when a set of instructions, rules or conditions contribute to items within the FormWorks 
system to continually repeat processing steps.  Ideally a loop continues until a finite set of conditions are met, 
terminating the loop.  However, if instructions, rules or conditions are not correctly defined, looping may continue 
unchecked.   
Looping can cause the bridges to constantly process fields/item(s) while also attempting to service client 
requests.  This scenario contributes to a decrease in the amount of keyable work available and a diminished work 
capacity.  After an excessive number of work records are looped into the cycle, the effective capacity can be 
decreased to only a few work records, after which users will simply see the "Waiting for Work" message.  
Looping is often initially identified with an error message displayed within Navigator (Alert Panel). 
 
Within FWEditor looping may principally be addressed within two primary areas. 
1. Fields shown in OCRepair that are not also shown in KE. 
2. Batch looping between DV and KE. 
As a best practice, contact your FIS technical representative before modifying or 
implementing changes to system configurations or functions.

Detection – Looping Fields In OCRepair Not Shown In KE 
Most often, looping that is not reflected in KE may be detected by viewing the Alert Display Panel within 
Navigator, the error message Suspected looping claim is displayed. 
Troubleshooting Looping Fields In OCRepair Not Shown In KE 
The looping caused by fields identified in OCRepair that are not reflected in KE can generally be remedied by 
utilizing the function ClearCaptureError which removes capture errors from selected fields in order to prevent 
looping (see the AC Functions document, ClearCaptureError function for details).   
Note: If the field in question is parsed into non-imaged fields, the OCRepair setting 
RejectTransferFields should be used to ensure the destination fields are populated at KE.     
 
Batch Looping between DV And KE 
Looping between a batch or batches may occur for multiple reasons.  
• Tables on Back Ground Servers (BGServers) are not in sync with tables on the keying stations.  An 
example of this scenario would be if DV did not find a lookup entry and put an error on the fields, then KE 
did find and remove the error, thus looping over and over.  
• An error is on a field that is not defined in the EntryGrid, rendering the keyer unable to resolve the error.   
Note:  This scenario may often be caused by an OCRepair Operator rejecting a field with F7 
line reject, or an AC Function, for example AlignInRows.  
 
• A selection list lookup is looping.  Occurring when the selection list inserts a value into a field, and that 
field changes value due to the application of a separate rule.
