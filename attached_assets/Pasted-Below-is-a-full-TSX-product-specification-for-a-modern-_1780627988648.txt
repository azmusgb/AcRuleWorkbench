Below is a full TSX product specification for a modern replica of the FormWorks / Document Capture Manager Editor. It is grounded in the actual editor model and wrapper surface, not just visual interpretation.

The most important grounding points are:

* FWEditor is a three-part workstation window: FWD Tree, Configuration Window, and Message Window.  
* The Editor is a GUI for defining pages, documents, batches, and the process/resource configurations associated with them in the .FWD database, with process/resource behavior controlled through PCMs.
* Rules are not flat rows. They are ordered rule lists with actions, sub-lists, and parent rules, forming a tree of rule evaluations.
* Page editing is image-template-centric, and page-level process access is contextual: from the page image’s processes panel or from the FWD tree. Field-level process access comes from right-clicking the field in the page image.  
* The wrapper surface supports the exact object hierarchy you need to reproduce: pages, variants, documents, batches, processes, resources, private process nodes, page/document traversal, raw STC child nodes, and page/variant field geometry.
* Navigator is a separate web monitoring/governance product with dashboard panels and left navigation, and should not be confused with FWEditor’s tree-driven configuration UX.

⸻

1. Product definition

1.1 Product goal

Build a TSX-based engineering workbench that replicates the Editor, not Navigator.

That means the product is primarily for:

* inspecting and editing the FWD object hierarchy
* configuring object-bound processes
* editing page geometry and variants
* managing resources
* editing rule trees
* inspecting raw node structures
* seeing messages/diagnostics continuously

It is not primarily:

* a dashboard
* a live-ops monitor
* a report center
* a workflow administration portal

1.2 Fidelity target

The implementation should preserve these editor truths:

1. Tree-first navigation
2. Selection-driven context
3. Multi-pane workstation layout
4. Image-backed page editing
5. Rule-tree editing with action sub-lists
6. Persistent message window
7. Heavy right-click/context interaction
8. Scope awareness at field/page/variant/document/batch/process/resource levels

⸻

2. Technology recommendation for TSX implementation

2.1 Frontend stack

Recommended:

* React
* TypeScript
* TanStack Router
* TanStack Query
* Zustand or Redux Toolkit
* React Aria or equivalent keyboardable primitives
* SVG + Canvas hybrid for image/field overlays
* AG Grid / TanStack Table for dense configuration grids
* Monaco only for raw/advanced panes where truly useful

2.2 Layout library

Prefer custom split-pane layout over generic dashboard kits.

Recommended:

* react-resizable-panels
* or custom splitter implementation

You need:

* persistent pane sizes
* nested split panes
* low-latency resizing
* docking-like behavior

2.3 Styling system

Use a stable design system, not utility drift.

Recommended:

* Tailwind or CSS Modules
* tokenized semantic colors
* very compact density scale
* mono typography for metadata/tokens
* square/low-radius panels
* explicit separators

12. Interaction contracts

12.1 Selection synchronization

When user selects:

* tree node → open/select workspace tab and inspector
* field on canvas → select grid row + inspector
* rule node → update rule summary + function editor
* raw child node → update viewer + metadata

12.2 Context menus

Required everywhere meaningful:

* tree nodes
* field overlays
* rule nodes
* resource rows
* raw node rows

12.3 Save model

Because FWEditor often saves on close, but you are building in TSX, model two modes:

Compatibility mode

* apply changes on focus switch/close

Safer modern mode

* in-memory dirty state
* explicit Apply/Save at object scope

If you are building read-only first, still wire the dirty-state model now.
